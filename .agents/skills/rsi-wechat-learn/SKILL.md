# 微信能力验证与报备

适用于本人及工程任务会话、好友和群聊回复会话。任务留在当前负责会话。
从[原请求与会话协作协议](../../../harness/DESKTOP-WECHAT.md)核身份、目标和回执。
新入站附有当前协议和收发入口的绝对路径时，从该入口核验；会话工作目录可能仍是旧版工作区。
确需另一会话协作时，核对用户授权和已有执行者，只交办一个有明确结果的子项，
再把证据汇回原负责会话。

## 尝试与验证

1. 找到第一处缺口。
   - **触发**看原生身份、入站持久化与 ACK，以及接收器中的原 ID、输入摘要、
     目标会话和附件。已入队但看不到输入时，维护按协议的只读对账入口核入队与
     实际轮次；轮次缺失保留为待复核。
   - **发送**从该轮冻结结果查到原 V2。沿协议的 `desktop_reply status` 查询
     同一 ID、会话和轮次。`pending` 表示等待回执，`unknown` 表示结果待确认，
     `not_sent` 表示未发送，`sent` 表示整条已发送。`partial` 表示部分已发送，
     说明已发段数并逐段引用 `texts`，剩余段已确认未发。
     `quiet` 保留为本轮静默决定。图片、文件和原生表情各按实际载体核验。
2. 先匹配本 Skill 的规则和[已有经验](../../../memory/lessons.md#微信会话复用经验)。
   例如链接回复的回执要核实际待发正文，原结果是结构化对象时按现有收发协议处理。
   遇到同类问题时直接应用适用规则，记录命中的小节和本轮结果。
3. 现有规则不适用时，在原授权内主动试一条可验证的做法。先确定哪条证据能说明
   做法有效，再用当前原件、同一原请求或隔离样本验证。普通聊天的权限以原包为准。
   代码、客户端操作和真实发送沿用各自授权。保持原 ID 和冻结结果，未知发送先查
   原回执。发现问题但尚未验证有效做法时，在原会话留断点和下一项可核证据。

## 验证后自动报备

已有[私有报备绑定](../../../harness/DESKTOP-WECHAT.md#learning-reports)时，验证成功后
用 Codex 会话消息工具给绑定的维护会话报一次，作为本轮收尾动作。首次启用或绑定
改变时，先核真实会话 ID 和记录的直接用户授权。报备留在 Codex 内。

- **候选**：本轮验证了可复用的新做法，写清它解决的条件和下次适用的入口。
- **复用**：一条后来的独立请求自行用上已发布的规则，并取得对应结果。每个回复
  会话对同一条规则只报首次有证据的复用。写明当前 Skill 小节或 Git 版本。

报备使用`【RSI 经验报备】`，带类别、原 Codex 验证轮次 ID、适用情形、采取的
做法、结果与可查证据、下次入口。发送前按原轮次和类别查已有报备，提交后在原轮次
记下结果。工具返回不明时先查维护会话中的同一报备。无可用渠道时把同一摘要留在
原会话，等维护核对。

报备只写脱敏摘要。图像、聊天正文、完整微信原 ID 和私有路径留在原记录。明确
证据属于隔离验证、已部署、真实读取或原 V2 送达；完成接口接受只证明已提交。
