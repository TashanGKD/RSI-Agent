# 原生调度工具缺失的诊断

先发现实际工具清单，不只查旧名称automation_update：应用迁移后也可能使用原生Automations连接器。Pages/Sites的任务工具不能冒充本地对话heartbeat。

2026-10-30本机只读代码检查发现，旧automation_update的提供条件是桌面、本地宿主、未选择hosted automations路径。hosted选择又依赖账号迁移及原生Automations连接器可用状态。由此只能提出可核验的原因，不能仅凭代码分支就宣称当前用户已迁移或工具已恢复。

可执行的只读诊断：
- 列出当前原生与连接器工具，分别确认旧入口和新入口。
- 对明确的Automations对象，通过现有Plugin Management检查权限；本机对象ID为connector_openai_automations。权限可用、已连接、工具暴露和实际调用是不同事实。
- 用现有正式只读应用目录能力检查连接器状态/工具目录。返回大目录时只保留目标对象元数据，不读无关业务；超时先重查同一读取，不推断服务已停止。
- 核目标对话是否持久、宿主与运行环境是否匹配。不要仅因source字段为vscode就断言它不是桌面对话；本机普通桌面对话也有这个值。
- 依官方支持的连接/目录刷新途径恢复；不要为暴露工具而改权限、功能发布开关、人工注册同名动态工具，或跳过工具层调用私有写接口。

尚未确认可用恢复途径时，留下具体新证据、已排除原因和下一步，保持原目标；不能反复把“工具缺失”本身当新进展。实际恢复后才按正式schema创建/读回任务，随后验证自然运行。只有配置草案或权限设置读回，不能宣布完成。

## 先查服务启动，再推断工具筛选

本机后续查到真实失败：目标对话codex_app的runtimeStatus=failed，toolsError为“Codex app tools pipe closed”；同一运行进程日志明确记录“untrusted-code-signing-identity”。先前仅检查工具目录、功能分支和权限，未查到此启动失败，不足以定位根因。

可靠的顺序是：确认本岗位运行环境→查询该thread的MCP服务状态→对照当前应用运行日志→核官方启动器使用的运行时与签名→按真实错误寻找正常重连/组件修复。全局当前选中远端并不等于该thread的环境。

这次官方未改启动器的只读initialize与tools/list测试也在目录返回前断开；应用及官方Node的磁盘签名检查通过，未见外部Node或注入环境标志，因此签名信任拒绝的更深原因尚未证实。不要把“签名有效”说成“连接一定获信任”，也不要关闭签名验证或更换身份来强行通过。

没有拿到实际工具目录时，不能声称当前一定选择了本地或hosted分支。全局MCP reload可能影响其他工作，不作为单岗位的默认修复；优先支持明确scope的恢复方式。

## 签名有效不等于启动链可信

进一步只读核实：本机launchctl的CODEX_CLI_PATH指向自定义共享入口；实际进程链为ChatGPT→NVM Node→官方CodexCLI。NVM Node由Node.js Foundation签名，官方组件由OpenAI签名。校验组件还检查父/祖父进程，这使自定义启动链成为信任拒绝的具体候选；不能只检查工具服务自身的磁盘签名。精确判定仍需正常修复后真实连接通过，不把静态字符串推断当完整实证。

正常恢复应优先核厂商默认启动方式与现有共享集成的冲突，按受支持生命周期重建连接。不要关闭校验、改信任名单、重签应用或用受信任的通用运行时替其他脚本代理身份。也不能为重启共享进程中断其他岗位。配置文件改完不会自动改变已运行进程的父链；手工启动的诊断进程父链又与正式启动不同，须保留这个限制。
